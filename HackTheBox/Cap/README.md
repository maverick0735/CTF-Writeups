2. 🌐 Web Enumeration & IDOR Exploitation
Navigating to http://10.129.69.192 exposes a web dashboard with a Security Snapshot (5 Second PCAP + Analysis) feature. When a snapshot is generated, the application redirects the user to a URL like http://10.129.69.192/data/1.

By modifying the integer in the URL path to http://10.129.69.192/data/0, I bypassed intended access controls and viewed a historical packet capture generated by the system administrator. I downloaded 0.pcap for offline analysis.

🧠 Vulnerability Deep Dive: IDOR (Insecure Direct Object Reference)
IDOR occurs when an application provides direct access to objects based on user-supplied input without validating if the user has the authorization to view that specific object. In this case, the web application trusted the user-supplied integer (0) in the URL path without verifying if my current session owned that specific PCAP file.

3. 📦 Packet Analysis & Initial Access
I opened 0.pcap in Wireshark. By filtering for ftp traffic and following the TCP stream, I discovered cleartext authentication credentials.

🧠 Vulnerability Deep Dive: Unencrypted Protocols (FTP)
File Transfer Protocol (FTP) was designed before modern encryption standards. It transmits all data—including usernames and passwords—in plain text. When the administrator logged into FTP while the server was capturing packets, their credentials were saved directly into the network traffic log. Anyone who can intercept the traffic (or access the PCAP via the IDOR) can read the password without needing to decrypt anything.

Establishing SSH Foothold
Since port 22 is open, and users often reuse passwords across services, I used the FTP credentials to establish an interactive SSH session:

Bash
ssh nathan@10.129.69.192
User flag obtained successfully.

4. ⚡ Privilege Escalation
Once on the system as a low-privileged user, I enumerated binary execution capabilities using getcap:

Bash
getcap -r / 2>/dev/null
Key Finding: /usr/bin/python3.8 = cap_setuid,cap_net_bind_service+eip

🧠 Vulnerability Deep Dive: Linux Capabilities
Linux capabilities are a security feature that breaks down the full privileges of the root user into smaller, distinct privileges. The cap_setuid capability allows a program to change its User ID (UID). Because the system administrator assigned cap_setuid to the Python 3.8 binary, anyone running Python can force the program to execute as root (UID 0), entirely bypassing the need for sudo passwords.

Root Exploitation
To exploit this misconfiguration, I executed a Python one-liner to spawn a root shell:

Bash
/usr/bin/python3.8 -c 'import os; os.setuid(0); os.system("/bin/bash")'
🧩 Payload Breakdown:
/usr/bin/python3.8 : Invokes the vulnerable Python binary.

-c : A flag telling Python to execute the following string as inline code rather than executing a .py file.

import os; : Imports the OS module, which allows Python to interact with the underlying Linux operating system.

os.setuid(0); : This is the payload's core. It commands the OS to set the current process's User ID to 0 (Root). Under normal circumstances, this would fail for a standard user. However, because the Python binary has the cap_setuid capability, the kernel permits the UID change.

os.system("/bin/bash") : Spawns an interactive Bash shell. Because the Python process running this command has successfully changed its UID to 0, the resulting Bash shell inherits root privileges.

Root flag obtained successfully.

🛡️ Remediation & Defenses
Fixing the IDOR: Implement proper session validation. Before serving /data/X, the application must check if the current user's session token is authorized to view object X.

Protocol Hardening: Completely deprecate FTP. Enforce SFTP (SSH File Transfer Protocol) or FTPS to ensure all data in transit is encrypted.

Least Privilege: Remove the cap_setuid capability from the Python interpreter using the command setcap -r /usr/bin/python3.8. Standard interpreters should never have root-level capabilities.
